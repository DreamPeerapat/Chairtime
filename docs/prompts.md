## 3. Seed data (สำคัญกว่าที่คิด)

> เขียน seed script สร้าง 3 ร้านที่มีลักษณะต่างกันจริง:
> 1. ร้านเล็บ — 4 โต๊ะ 3 ช่าง บริการ 12 รายการ 30-120 นาที
> 2. ร้านผม — 5 เก้าอี้ 4 ช่าง มีบริการย้อมผมที่ใช้ service_segment แบบ active/passive
> 3. ร้านนวด — 6 เตียง 8 หมอนวด มี buffer ทำความสะอาด 15 นาที
> ใส่ booking ย้อนหลัง 30 วันและล่วงหน้า 14 วัน ให้ดูเหมือนร้านจริง
> ข้อมูล 3 ร้านนี้จะเป็นตัวทดสอบว่า schema รองรับได้จริงหรือไม่

## 4. Availability engine (ใช้ plan mode)

กด `Shift+Tab` เข้า plan mode ก่อน:

> อ่าน docs/logic.md ข้อ 1 ให้ละเอียด
> วางแผนการ implement lib/availability/ โดยยังไม่ต้องเขียนโค้ด
> บอกผมว่าจะแบ่งไฟล์ยังไง แต่ละไฟล์รับผิดชอบอะไร
> และมี edge case อะไรบ้างที่คุณเห็นแล้วผมยังไม่ได้เขียนไว้ใน docs

จากนั้น:

> เขียน test ก่อน implement
> ครอบคลุมอย่างน้อย: พักเที่ยง, ช่างลาครึ่งวัน, buffer ชนกัน,
> ย้อมผม passive segment ที่ช่างต้องว่างให้คนอื่นได้,
> จอง 2 บริการต่อกันต้องได้ช่างคนเดียวกัน,
> ข้ามเที่ยงคืน, วันที่ร้านปิด, resource ไม่พอ
> รันแล้วให้ fail ทั้งหมดก่อน แล้วค่อย implement ให้ผ่าน

## เทคนิคการใช้งาน

**แบ่งงานให้เล็ก** — 1 คำสั่ง = 1 โฟลเดอร์ หรือ 1 ฟีเจอร์ ไม่ใช่ 1 phase

**ใช้ plan mode กับงานยาก** — `Shift+Tab` ก่อนสั่งงาน availability หรือ loyalty
ให้มันวางแผนให้ดูก่อน แก้แผนถูกกว่าแก้โค้ด

**`/clear` บ่อยๆ** — จบ 1 ฟีเจอร์แล้วเคลียร์ context ไม่งั้นมันจะเริ่มลืมกฎใน CLAUDE.md

**commit ทุกครั้งที่ test ผ่าน** — ให้มัน commit เองด้วยข้อความที่สื่อความ

**แก้ CLAUDE.md แทนการเถียง** — ถ้าต้องแก้เรื่องเดิมซ้ำสองครั้ง นั่นคือสัญญาณว่า
กฎยังเขียนไม่ชัด ไปเพิ่มบรรทัดใน CLAUDE.md แทนที่จะบอกซ้ำในแชท

**อย่าเชื่อคำว่า "เสร็จแล้ว"** — สั่งให้รัน test และแปะผลลัพธ์จริงมาให้ดูทุกครั้ง

**ให้มันอ่าน seed data ก่อนออกแบบ UI** — จะได้ UI ที่ตรงกับข้อมูลจริง ไม่ใช่ข้อมูลสมมติสวยๆ

## สัญญาณอันตราย

หยุดแล้วตรวจทันทีถ้าเจอ:

- มันสร้าง table ใหม่ที่ไม่มีใน schema.sql → schema ออกแบบผิด หรือมันเข้าใจผิด
- มันเขียน `SELECT ... WHERE NOT EXISTS` ก่อน insert booking → ละเมิดกฎข้อ 1
- มันเขียน `UPDATE point_ledger` → ละเมิดกฎข้อ 2
- มันใช้ `new Date()` คำนวณเวลาธุรกิจ → จะพังเรื่อง timezone แน่นอน
- query ที่ไม่มี `tenant_id` → ข้อมูลรั่วข้ามร้าน
- test ผ่านหมดตั้งแต่ครั้งแรกโดยไม่เคย fail → test เขียนหลอกตัวเอง
