## 🔒 24 กันยายน 2026 — ปิดช่องสมัครฟรีตลอดไป + งานค้างหลังบ้าน

**ช่องโหว่ที่ปิด:** แพ็กเกจเสียเงินตอนสมัครจบที่ปุ่ม "ยืนยันว่าโอนเงินแล้ว" ซึ่ง
เปิดร้านเป็น `active` โดยไม่มีทั้ง `paid_until` และ `trial_ends_at` — cron หมดอายุ
ข้ามร้านที่ไม่มีวันที่ ร้านจึงใช้ฟรีได้ตลอดไปด้วยการกดปุ่มเดียว

**แก้แบบที่ตัดสินใจไว้:** ทุกการสมัครเริ่มเป็น trial (ความยาวจากแพ็กเกจ `trial`)
เก็บแพ็กเกจที่เลือกไว้ใน `plan_id` ให้หน้าแพ็กเกจเสนอก่อน แล้วจ่ายผ่านหน้าแพ็กเกจ
ซึ่งตรวจสลิป ระหว่าง trial ได้สิทธิ์แบบ Basic เสมอแม้เลือก Pro
(`entitlementsForTenant` — ยังไม่เคยจ่าย + มี `trial_ends_at` = trial)
`/onboarding/payment` เหลือไว้ให้ร้านที่ค้าง `pending_payment` จากของเดิมกดเริ่ม trial

**ร้านที่อาจหลุดไปแล้ว** — ตรวจบน production ด้วย:
`SELECT id, name, created_at FROM tenant WHERE status='active' AND paid_until IS NULL AND trial_ends_at IS NULL;`
ยังไม่ได้แก้ข้อมูลให้ — ต้องตัดสินใจรายร้าน

**ของใหม่อื่น:**
- เตือนเจ้าของร้านทาง LINE ก่อนหมดอายุ 7 วันและ 1 วัน (`lib/billing/expiry-reminder.ts`,
  template `plan_expiring`) เข้าคิวจาก `/api/cron/trial-expiry` ส่ง 09:00 เวลาร้าน
  worker อ่าน tenant ใหม่ก่อนส่ง ร้านที่ต่ออายุแล้วจะไม่ได้ข้อความ
- แก้ `service_segment` ในหน้าบริการได้แล้ว (`components/admin/segment-editor.tsx`,
  ตรวจที่ `lib/admin/service-segments.ts`) — แทนที่ทั้งชุด มีผลกับคิวใหม่เท่านั้น
- หน้าตั้งค่าระดับสมาชิก `/dashboard/settings/loyalty/tiers` (ซ่อนตาม `LOYALTY_ENABLED`)
  แก้ได้เฉพาะช่องที่โค้ดใช้จริง — `discount_percent` และ `priority_booking_days`
  **ยังไม่มีโค้ดไหนอ่าน** จึงไม่ได้ใส่ในฟอร์ม
- แตกไฟล์ที่เกิน 200 บรรทัดตามกฎใน CLAUDE.md

**ทดสอบ:** unit ผ่านทั้งหมด · typecheck / lint ผ่าน · integration + e2e **ยังไม่ได้รัน**
(ไม่มี Docker ในเครื่องที่ทำ) · ยังไม่ได้เปิดหน้าจอจริง เพราะ `.env.local` ชี้ Neon

**ทำไมเขียน QR encoder เอง:** ทางเลือกคือยิงยอดเงินกับเลขพร้อมเพย์ไปให้
`api.qrserver.com` วาดให้ (หน้า LINE ทำแบบนั้นอยู่) หรือเพิ่ม dependency
ซึ่ง CLAUDE.md ห้ามโดยไม่ถาม — เลยถามแล้วเลือกเขียนเอง QR เป็นสเปกที่นิ่งแล้ว
(ISO/IEC 18004) รองรับแค่ byte mode + ระดับ M + version 1–10 ก็พอ
(213 ไบต์ ส่วน payload พร้อมเพย์ยาว 84)

**พิสูจน์ว่าอ่านได้จริง:** ไม่ใช่แค่เทสต์โครงสร้าง — generate ออกมาแล้วถอดรหัส
กลับด้วย jsQR (ติดตั้งนอกโปรเจกต์ ไม่ได้แตะ `package.json`) ครบทุก version
1–10 ได้ payload ตรงเป๊ะทุกอัน `tests/unit/qr.test.ts` เก็บลายนิ้วมือของ
สัญลักษณ์หนึ่งอันไว้ เพราะ QR ที่ mask ผิดยังดูเหมือน QR ทุกประการ แต่สแกนไม่ติด

**การตัดสินใจเรื่องเงิน (ถามก่อนแล้ว):** ถ้าตั้ง `SLIPOK_API_KEY` แล้วบริการ
ตอบว่าไม่พบรายการ/ยอดไม่ตรง → **ไม่ต่ออายุ ไม่เขียนแถว** บอกเหตุผลที่บริการ
ให้มาเป็นภาษาไทยแล้วให้แก้แล้วแจ้งใหม่ ส่วน "เรียกบริการไม่ได้" ไม่ถือเป็นคำตอบ
— กรณีนั้นได้ `unchecked` แล้วต่ออายุให้ตามเดิมเหมือนก่อนมีฟีเจอร์นี้

## บั๊กที่เจอระหว่างทาง (เจอด้วย test ทั้งหมด)

**2. TRUNCATE ต้องเป็นเจ้าของตาราง**
role แอปไม่มีสิทธิ์ (ตั้งใจ) — seed จึงต้อง truncate ผ่าน connection admin

เดิมยกเว้น lead time ด้วยการแกล้งย้อนนาฬิกา 1 ปี ซึ่งดันไปทำให้ทุกวันเลย

`lib/loyalty/tier.ts`, `lib/loyalty/birthday.ts`, `lib/loyalty/rewards.ts`
ตาม `docs/logic.md` ข้อ 3.5 และ `docs/roadmap.md` Phase 6 ทุกข้อ — เขียน
test ก่อน implement ตามที่ CLAUDE.md บังคับสำหรับ `lib/loyalty/`

**tier.ts** — คำนวณทุกวันผ่าน `/api/cron/loyalty` เทียบทุก tier จากสูงไปต่ำ
ด้วย `qualify_window_months` **ของ tier นั้นๆ เอง** (ไม่ใช้ window เดียวกันทุก
tier) ขึ้นทันทีถ้าผ่านทั้งยอดใช้จ่ายและจำนวนครั้ง — ลงมี grace period 30 วัน
(ครั้งแรกที่ตกเกณฑ์แค่เตือน + ตั้ง `valid_until` ยังไม่ลด พอผ่านกำหนดค่อยลด
จริงไปยัง tier สูงสุดที่ยังผ่านเกณฑ์ ไม่ใช่ไม่มี tier เสมอไป) `is_manual`
กัน cron ไม่ให้แตะ tier ที่แอดมินตั้งเองเด็ดขาด

**birthday.ts + bonus.ts** — `point_ledger_idem` ใช้กับโบนัสวันเกิดไม่ได้
(เป็น "ครั้งเดียวตลอดกาล" แต่วันเกิดต้องให้ซ้ำได้ทุกปี) เลยแยกเป็น
`grantBonusPoints()` ที่ใส่ `source_id: null` แล้วเช็คกันซ้ำเองด้วย
`hasBonusSince()` (มีแล้วในปีนี้หรือยัง) แทน — บันทึกเหตุผลไว้เป็นคอมเมนต์
ในโค้ดเพราะเป็นจุดที่ pattern เดิมของ Phase 5 ใช้ไม่ได้

**rewards.ts** — แลกแต้มเป็นของรางวัลจากแคตตาล็อก (`listRewardsForCustomer`
กรองตาม tier/สต็อก/ช่วงวันที่ให้อัตโนมัติ) ผ่าน `redeemReward()` แล้วออกโค้ด
6 หลักให้ลูกค้า จุดที่ตัดสินใจกลางทาง: `redeemPoints()` เดิมของ Phase 5 มีกฎ
เฉพาะการจ่ายบิล (ขั้นต่ำ/สูงสุด % ของบิล) ที่ใช้กับการแลกของรางวัลไม่ได้ (ของ
รางวัลมี `point_cost` ตายตัว) เลยแยก `deductPointsFifo()` ออกมาเป็นแกนกลาง
FIFO+lock ที่ใช้ร่วมกัน ส่วนกฎเฉพาะทางแยกอยู่คนละฟังก์ชัน

**useRewardCode()** — ให้พนักงานเช็คอินโค้ดที่เคาน์เตอร์ เจอบั๊กระหว่างเขียน
test: ตอนแรกให้ฟังก์ชันนี้ mark สถานะ `expired` แล้ว throw error ในทรานแซกชัน
เดียวกัน แต่ `withTenant` ห่อทุกอย่างเป็น 1 transaction — throw ทำให้
transaction ทั้งก้อน rollback รวมถึงการ mark expired ด้วย (เขียนแล้วไม่เคย
persist จริง) แก้โดยย้ายการ mark expired ไปเป็น sweep แยกต่างหาก
(`expireRewardCodesForTenant`) ที่รันใน cron ทุกวันแทน — `useRewardCode()`
เองก็ยัง refuse โค้ดหมดอายุถูกต้องอยู่แล้วแม้ status ในตารางจะยังไม่ถูกอัปเดต
(เช็ค `expires_at` ตรงๆ ทุกครั้ง ไม่ได้พึ่ง status อย่างเดียว)

**UI ฝั่งร้าน** — `/dashboard/rewards` (จัดการแคตตาล็อก, ต้อง manager ขึ้นไป)
กับ `/dashboard/rewards/redeem` (เช็คอินโค้ด, staff ทุกคนใช้ได้ — แยกสิทธิ์
เพราะพนักงานหน้าร้านต้องเช็คอินโค้ดได้ทุกวัน แต่ไม่ควรแก้แคตตาล็อก) นำทาง
ไขว้กันได้ทั้งสองทาง ปุ่มนำทางหลักในเมนูชี้ไปหน้าเช็คอินเพราะเป็นหน้าที่ใช้
บ่อยกว่า

**UI ฝั่งลูกค้า** — `/{tenantSlug}/rewards` (LIFF) ใช้ identity model เดียว
กับหน้าแต้มเดิม (`liff.getAccessToken()` แล้วให้ server ยืนยันกับ LINE เอง
ไม่เชื่อ `lineUserId` จาก client) แลกแล้วได้โค้ดกลับมาโชว์บนจอทันที เชื่อม
ลิงก์ไป-กลับกับหน้า `/points` เดิม

**ยังไม่ได้ทำ (นอกเหนือจาก Phase 6):** ยังไม่มีหน้าแอดมินสำหรับตั้งค่า
`membership_tier` เอง (ระดับ, ยอดใช้จ่าย/จำนวนครั้งที่ต้องผ่าน, ส่วนลด) —
roadmap Phase 6 ไม่ได้ระบุไว้ชัดว่าต้องมี UI ส่วนนี้ ตอนนี้ตั้งผ่าน DB
โดยตรงเหมือน `service_segment` การแก้ payload ของ discount ก็ยังทำผ่านฟอร์ม
ของรางวัลตรงๆ ไม่มี preview ว่าลูกค้าจะเห็นส่วนลดจริงเท่าไหร่ตอนใช้บริการ

`import()` หลัง `loadEnv()` แทน static import — ยังไม่ได้แก้เพราะนอกขอบเขต
งานนี้
